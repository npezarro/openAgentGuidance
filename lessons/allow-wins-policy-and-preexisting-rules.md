# In an allow-wins policy engine, enumerate the rules already present before adding narrowly scoped ones

Where a policy system grants access if any rule permits it, a single broad permit rule makes every restrictive rule added afterward decorative. Enumerate what already exists for the resource being protected, and remove or disable the broad entries, before writing anything new.

The failure is invisible by construction. The carefully scoped rules exist, are enabled, and read exactly as intended when listed back. Nothing in that view reveals that a pre-existing unrestricted permit for the same resource is deciding every request first. Automated installation is a common source of such rules, since setup routines frequently add a blanket permit for their own component so that the component works everywhere, with no restriction on port, interface, source range, or context.

Two second-order points follow. Determine whether the broad rule is created once at installation or re-created every time the component starts, because that decides whether disabling it persists at all. And if the creation step permits unconditionally rather than checking first, an upgrade will restore it, so the hardening is one version bump from being undone; record that as an outstanding risk rather than treating the work as finished.

When scoping a restriction, combine two independent conditions that must both hold (for example a specific interface and a specific permitted address range) rather than relying on a category label the platform can reassign on its own, which silently widens the rule. Finally, do not establish a negative by reading a rule list back to yourself. Rules describe intent; reachability is the fact. Test from a vantage point genuinely outside the boundary being claimed. And distinguish "verified closed" from "rule provisioned but not yet exercised," since components that bind resources only during an active session will appear closed at idle for reasons unrelated to the rule.
