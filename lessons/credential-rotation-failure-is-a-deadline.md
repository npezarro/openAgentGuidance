# A broken credential rotation is a countdown, not a steady state, and the countdown is silent

When automated credential rotation stops working, treat it as a deadline with a fixed expiry date rather than a degraded-but-stable condition. Alarm on remaining credential lifetime, not on rotation job success.

The mechanism is a long-lived credential that carries its own expiry, separate from the short-lived tokens it mints. Ordinary refreshes consume it without extending it; only a full re-issue, which typically requires interactive human involvement, resets the clock. So the system keeps working perfectly for the entire remaining lifetime of that credential, which may be weeks. Every observable signal during that window says healthy. Then the credential expires, refresh fails, and recovery requires exactly the interactive step that the original breakage was blocking. Failures cluster mysteriously because each component dies a fixed interval after its own last successful rotation, not when rotation broke.

Long silent runway is also what makes muting the failure notification feel safe. The reasoning "nothing broke after it was disabled, so it was noise" is valid for days and false for weeks, and the evidence supporting it accumulates right up until the outage.

Apply this by monitoring the expiry timestamp of the long-lived credential directly, with a warning threshold and a paging threshold expressed in days remaining. That single field measures both how long until the credential is unrecoverable and how long rotation has been failing, and it does not depend on knowing why rotation stopped. This matters because rotation can fail quietly: a pre-flight check that exits successfully when a prerequisite is merely absent produces no error at all, which is correct behavior for one night and an outage over a fortnight. Also ensure automated jobs clean up the transient state they create, since leftover artifacts from one run are a common cause of the next run's failure.
