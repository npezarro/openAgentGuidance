# Commands that resolve their target from shared mutable state are unsafe when anything else can change that state

When an operation infers what it acts on from ambient context (a selected environment, an active context, a current working state, a default target) and that context is shared with other actors, name the target explicitly instead. Where the tooling allows it, operate on a private copy of the context rather than the shared one.

The mechanism is check-then-act across a window. Reading the ambient selection and confirming it is correct establishes only what was true at the moment of the read. Any concurrent actor can change the selection before the operation runs, and the operation then applies to a target that was never inspected. Re-checking immediately beforehand narrows the window without closing it; it converts a reliable failure into an intermittent one, which is worse. A clean or expected-looking status output is not evidence that the selection will still hold, and the operation itself usually succeeds, so the damage surfaces only at a later step or on someone else's work.

Apply this by passing the target as an explicit argument at the point of the operation, by referring to an immutable identifier rather than a movable label, and by acquiring an isolated context for multi-step work so that no other actor shares the state being mutated. When recovering from a mistake of this kind, first preserve the misplaced work under a stable identifier, then redo it correctly against the intended target, then restore the affected shared state to exactly what its owner last set, and leave the ambient selection where they left it rather than resetting it to what is convenient.
